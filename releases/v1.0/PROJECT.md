# PROJECT — модель проекта: файлы, реестры, жизненные циклы

Основание: проекты устроены по-разному, а полезные находки одного проекта (уроки и
приёмка, реестр происхождения, словарь имён) не доходят до других. Поэтому в каждом проекте
одинаковы и имена файлов, и форма записей. Проекты различаются содержимым и фактами, а не устройством.

Этот файл — часть закреплённого kit (`agent-kit/vX.Y/PROJECT.md`), не путать с файлами
проекта в `docs/`. Полномочия он не меняет: кто что решает — `CORE.md`, «Полномочия».

## 0. Когда что читать

| Действие | Что прочитать в проекте |
|---|---|
| любой старт | вход, `## Project summary` в `docs/STATUS.md` |
| работа по теме, план, интерпретация результата | открытые и относящиеся к теме записи `docs/LESSONS.md`; `docs/DIRECTION.md` |
| выбор, запуск или правка объекта (чекпойнт, датасет, выпуск) | его запись в `docs/PROVENANCE.md` |
| новое имя запуска или объекта | `docs/NAMES.md` |
| работа по правилам ремесла, их изменение | `docs/RULES.md` и нужную спецификацию из его индекса |
| операция на инфраструктуре | `docs/OPERATIONS.md`, модули по их условиям |
| вопрос владельцу, действие под ограничением | `docs/DECISIONS.md` |
| создание или правка любого из этих файлов, переезд на раскладку | этот файл kit, нужный раздел |

Справочник читается по разделам, по условию; целиком — только при переезде.

## 1. Раскладка

Одни и те же имена во всех проектах. Файл заводится, когда у проекта появляется то, что в
нём живёт; пустых файлов «для комплекта» нет. Но если это есть, то оно живёт здесь и под
этим именем.

| Путь | Что в нём | Обязателен |
|---|---|---|
| `AGENTS.md` | вход (§9) | да |
| `CLAUDE.md` | `@AGENTS.md` (и строка локального слоя, где он есть, §11) | да |
| `README.md` | для человека: что это и как запустить | по потребности |
| `docs/STATUS.md` | `## Project summary` (kit `STATUS.md` §2), затем текущая картина | да |
| `docs/DIRECTION.md` | цель, открытые вопросы, порядок шагов (§5) | когда есть план дальше одного шага |
| `docs/RULES.md` | индекс действующих правил ремесла и спецификаций (§6) | когда есть свои правила работы |
| `docs/LESSONS.md` | реестр уроков (§2) | да, у рабочих проектов |
| `docs/DECISIONS.md` | вопросы владельцу и его решения (§3) | да, у рабочих проектов |
| `docs/PROVENANCE.md` | реестр или индекс происхождения (§4) | когда есть долговечные артефакты |
| `docs/OPERATIONS.md` | операционные факты: хосты, аккаунты и чьи они, пути, окружения, префикс имён заданий (модуль `clusters` §3), известные сбои | когда есть инфраструктура |
| `docs/NAMES.md` | словарь имён запусков и объектов | когда имена строятся по грамматике |
| `docs/HISTORY.md` | хронология (§8) | да |
| `docs/reports/ГГГГ-ММ-ДД-тема.md` или `…/тема/` | отчёты (§7) | по потребности |
| `docs/reference/` | технические справочники: модель данных, форматы, разобранные примеры, подробные спецификации, ADR | по потребности |
| `agent-kit/vX.Y/` | копия переносимого набора выпуска (kit `STATUS.md` §3) | да |

- **Расширения допустимы** и называются во входе в строке `extensions`: координация агентов
  (CHANNEL, BOARD), автоматизации, документы безопасности и участия, генерируемые
  инвентари, файлы зависимых репозиториев. Новые обязательные реестры для них не нужны.
- Номера записей — внутри проекта; из другого проекта пишется проект: `proj-b L-012`.
- При переезде прежние номера (например, DL-035, A-021) не перенумеровываются, прежние якоря
  остаются рабочими (явный якорь в заголовке). Новые записи продолжают прежнюю серию.
- Файл больше примерно 2 000 строк делится по месяцам (`docs/history/ГГГГ-ММ.md`) с
  индексом в основном файле; заголовки разделов при делении не меняются.
- Код, конфиги и данные раскладываются как принято в проекте; модель касается документов
  для работы агентов и владельца.

## 2. Уроки — `docs/LESSONS.md`

Что проект узнал. Хронология отвечает на «что было», уроки — на «что мы теперь знаем и
насколько уверены». В исследовании урок — научный вывод, в продукте — вывод о дизайне.
Уроки о поведении агентов, общие для всех проектов, — в `LESSONS.md` самого kit.

```markdown
### L-012 — <вывод одной строкой>
- date: 2026-09-29
- scope: где верно — модель, семейство, рецепт, весь проект
- observation: что видно, со ссылками на доказательства (отчёт, запуск, коммит, трекер)
- claim: вывод отдельно от наблюдения
- status: open | under test | established | refuted | superseded
- encoded: где вывод стал правилом (RULES, рецепт, тест) — если стал
- next: что проверит вывод — только для open и under test
- по потребности: alternatives, limitations, replaced by: L-…, changes: дата — что изменилось в выводе и почему
```

- Запись заводится, когда наблюдение появилось, включая отрицательные результаты и
  неподтверждённые гипотезы. Новое доказательство обновляет запись, а не порождает новую.
- Вывод не сильнее доказательства (CORE, «Эпистемика»); `established` требует
  воспроизведения или прямого доказательства.
- `encoded` — факт внедрения, а не степень уверенности. Если урок с `encoded` опровергнут,
  связанное правило или тест пересматривается в той же работе.
- Опровергнутое и заменённое не удаляется, иначе его проверят второй раз.
- Статус урока — оценка агента, не решение владельца.

## 3. Вопросы и решения — `docs/DECISIONS.md`

Место для того, что решает владелец по CORE («Полномочия»): приёмка результата, выход за
поручение, ресурсы и новые эксперименты, публикация, исключение из правила, выбор, который
он оставил за собой. Выборы агента в пределах поручения сюда не пишутся: они — в хронологии с
обоснованием и ссылкой на урок. Техническая спецификация, написанная агентом, — в RULES
(§6), даже если она действует только для одного семейства; в DECISIONS попадает только
решение владельца о ней со ссылкой на неё.

```markdown
### Q-007 — <предмет>
- state: open | answered → D-… | withdrawn (почему) | superseded → Q-… | reopened (дата, почему)
- since: 2026-09-29
- question: на что можно ответить да/нет или выбором из названных вариантов
- look at: конкретные материалы, без «прочитай всю ветку»
- changes: что изменится в зависимости от ответа

### D-021 — <решение одной строкой>
- date: 2026-09-29 14:05 (или unknown)
- outcome: accepted | rejected | chosen: … | authorized: … | exception: …
- scope: общее правило проекта | артефакт и ревизия | только для <X>
- source: цитата владельца, канал и время (или unknown — не восстанавливать по догадке); ответ на Q-…
- по применимости: supersedes: D-…; reopens if: условие; expires: условие
```

- Закрытый вопрос остаётся на месте с состоянием и ссылкой; сводка (`needs_user`)
  ссылается на открытые.
- `expires` ставится только решению, которое действительно временное; приёмка ревизии —
  исторический факт и не истекает, даже когда появился новый вариант.
- Прежняя запись, где вопрос и ответ в одном месте (например, A-…), остаётся одной записью со
  своим состоянием; дубль D не заводится.
- Вход не пересказывает решения: в его ограничениях — строки со ссылкой на D (§9).

## 4. Происхождение — `docs/PROVENANCE.md`

Что это за объект, откуда он и что о нём достоверно известно.

```markdown
### P-031 — <имя объекта>
- kind: checkpoint | dataset | run | code snapshot | release | cache
- identity: sha256 / полный SHA / run id — или unknown; источник идентичности
- copies:
  - <хост:путь> — referenced | observed | verified (дата, метод, охват) | unavailable (дата)
- made by: ревизия кода, конфиг (хеш), команда или отчёт — что известно
- relations: trained from P-…; code; config; data P-…; compatible with P-… (чем проверено)
- state: live | frozen | retired | deleted (дата, кем)
- constraints: кто может менять или удалять; ссылка на разрешение
```

- Упоминание пути не значит наличия файла; наличие не значит, что хеш проверен;
  совпадение размерностей не значит совместимости; run id не подтверждает чекпойнт или
  resume. Каждая копия проверяется отдельно, с датой и методом.
- Неизвестное пишется как unknown, без выдуманного хеша.
- `constraints` описывает ограничения и где лежит разрешение; сам по себе он права не даёт
  (CORE).
- Если реестр ведётся во внешнем инструменте или свидетельства лежат отдельно
  (`evidence/`, база запусков), `PROVENANCE.md` — индекс: что там, кто владелец, охват, как
  найти объект. Сами свидетельства не переносятся в Markdown.
- Научные поля запуска — по модулю `research-experiments` §5, запись ссылается на них.

## 5. Направление — `docs/DIRECTION.md`

Цель; открытые вопросы или гипотезы, у каждого — что на него ответит (L-…); шаги по порядку
с состоянием; что вне охвата. Шаги, которые владелец поручил или утвердил, ссылаются на D;
перестановки в пределах поручения агент делает сам и пишет в хронологию. Треки сводки
(STATUS §2) — текущий срез направления.

## 6. Правила ремесла — `docs/RULES.md`

Индекс того, как в проекте правильно делать работу: спецификация продукта, протокол
эксперимента, лестница проверок с числами, рецепты, интерпретация метрик, грамматика имён
(если нет NAMES). Каждая строка индекса: правило или документ; область действия (весь
проект, семейство, прототип); степень — норма | справка | предложение | черновик; источник
(L-…, D-…, ревью). Короткие правила пишутся прямо здесь, подробные спецификации и ADR — в
`docs/reference/`, индекс указывает на них. Общие правила работы — в kit.

## 7. Отчёты — `docs/reports/`

Снимок одного исследования: запуск, аудит, ревью, разбор сбоя, анализ, предложение, выпуск.
Имя `ГГГГ-ММ-ДД-тема.md` или каталог с `README.md` и материалами. Дата — дата события, если
она известна из текста; иначе дата добавления с пометкой `(добавлено)`; иначе `undated-тема`.
Совпадение имён в один день — суффикс `-2`. Первые строки: тип, вопрос, вердикт, автор и
ревьюер, ревизия рассмотренного материала.

- Отчёт по содержанию не правится; допустима только механическая правка ссылок при
  переезде. Исправление добавляется в конец с датой.
- Действующие факты не живут в отчётах: вывод уходит в уроки, решение — в решения, объект —
  в происхождение, а отчёт остаётся доказательством.

## 8. Хронология — `docs/HISTORY.md`

Только дописывается. Короткая запись на существенное событие: что изменилось, почему и
ссылка на D, L, P или отчёт. Анализ — в отчёты и уроки. Время — в часовом поясе владельца, с поясом. Какие события
существенны — в модулях. Порядок записей — порядок дописывания; при параллельных сессиях он
может расходиться со временем. Порядок по времени — по заголовкам; записанное не
переставляется.

## 9. Вход — `AGENTS.md`

Ориентир — около 60 строк; экономию проверяют замером чтения (kit README), а не числом строк.

1. Что это за проект — два-три предложения.
2. Что читать: всегда (CORE выпуска, `## Project summary`); по условию — таблица §0 для этого
   проекта, модули по их условиям.
3. Действующие ограничения — только то, что запрещает или ограничивает действия, строка со
   ссылкой на D-… или правило.
4. Блок `## Agent kit` (kit `STATUS.md` §3).

Во входе нет карты файлов (кроме отклонений), инструкций по запуску (README, RULES),
текущего состояния и истории решений.

## 10. Рабочие копии и канон

У проекта одно **каноническое место**: там интегрируются статус, реестры и хронология (путь —
во входе). Остальные копии бывают трёх видов:

- **dev-копия или ветка задачи** (изменяемая): читает канонические файлы с их ревизией, если
  доступны; для вопросов о своём коде верит своей ветке. Результат пишет отчётом передачи в
  своих `docs/reports/` (или в передаче хода), не выдавая состояние ветки за состояние
  канона. Интегрирует владелец канона.
- **копия без доступа к канону** (например, кластер без доступа к основному компьютеру): пользуется синхронизированной
  проверенной копией с ревизией и датой; живое состояние — unknown; результат — отчётом
  передачи, сверка — при следующей синхронизации.
- **замороженный снимок** (эксперимент, архив): не меняется ради модели; читается как
  исторический, со своей ревизией.

Указатель «это не каноническая копия; канон — <путь>» добавляется только в изменяемые копии.
Закрыть ненужную копию — решение владельца.

## 11. Отклонения

Отклонение пишется во входе в строке `deviations` с причиной. Известные:
- **Лабораторный репозиторий:** в Git только короткий английский вход с правилами проекта. Модель проекта живёт в рабочей области владельца или в неотслеживаемом слое;
  `CLAUDE.md` подключает и вход, и локальный слой (`AGENTS.local.md`); отчёты в
  отслеживаемых `docs/` сохраняют принятые там имена.
